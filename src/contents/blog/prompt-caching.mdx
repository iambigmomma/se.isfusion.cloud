### Introduction

A security intelligence team was running an AI agent at scale. Every time their agent analyzed a new threat, it sent a prompt containing the same 4,000-token system instruction, the same tool definitions, the same analysis framework — followed by the specific threat data to evaluate. Their prompt cache hit rate: **7%**.

They made one structural change: moved a single dynamic identifier from the middle of the prompt to the end. Their hit rate jumped to **74%** — and stayed there. Their monthly inference bill dropped by 59%.

[This is a documented production case](https://projectdiscovery.io/blog/how-we-cut-llm-cost-with-prompt-caching), not a theoretical optimization. And it represents one of the most common patterns in production LLM deployments: teams that have prompt caching configured correctly in principle but are getting almost none of the benefit — because one dynamic field in the wrong position breaks the entire cache.

This article explains how prompt caching actually works, why most implementations get it wrong, and the concrete steps to move from single-digit hit rates to the 60–80% range that's achievable in production.

### Key Takeaways

* Prompt caching is the single highest-leverage cost *and* latency optimization most teams haven't fully exploited.
* There are three distinct caches, often confused: KV (automatic, within a request), prefix/prompt (cross-request, **you control it via prompt structure**), and semantic (application-layer, for repeated queries).
* Cache reads cost ~10% of the input rate (a 90% discount); at a 1.25× write premium you break even after about **one** cache hit, so caching almost always pays off.
* There's a minimum cacheable prefix length, and it moves with the model generation: older Claude 3.x models cache prefixes as short as 1,024–2,048 tokens, while Claude Haiku 4.5 requires 4,096.
* The #1 failure mode: a dynamic field (timestamp, session ID) embedded in an otherwise static prompt breaks the whole prefix — one team went from 7% to 74% hit rate by moving a single field to the end.
* Put all static content first, all dynamic content last, and track cache hit rate as a first-class metric. 60–80% is realistic — and it cuts latency, not just cost.

### The Three Caches You Need to Understand

"Caching" means three different things in the LLM inference context, and confusing them leads to misplaced optimization effort. Here's a clear taxonomy:

**1. KV Cache** — happens automatically, inside a single request

When a model generates a response, it computes key-value attention states for each input token. Without a KV cache, each decode step would recompute attention over all previous tokens. The KV cache stores these states so decoding is incremental. This is always on, requires no configuration, and speeds up response generation within a single request. You don't control it; you benefit from it automatically.

Think of this like a translator who writes notes as they work through a document — they don't re-read the first paragraph every time they translate the fifth.

**2. Prompt Cache (Prefix Cache)** — cross-request, controlled by you

Prefix caching extends the KV cache concept across multiple independent requests. When multiple requests share the same leading tokens — the same system prompt, the same few-shot examples, the same reference documents — the model reuses the computed KV states from the first request instead of recomputing them on every call.

This is the cache described in the rest of this article. It requires you to structure your prompts correctly. When it works, it's the single biggest cost lever available.

Think of a teacher who has prepared detailed lesson notes once. Every time a new student asks a question, the teacher doesn't re-read the entire curriculum from scratch — they pull from the prepared notes and only process the specific new question. The notes are the cacheable prefix; the student's question is the dynamic tail.

**3. Semantic Cache** — application-layer, separate system

Semantic caching stores complete input-output pairs and retrieves them when a new query is semantically similar to a previous one, based on embedding similarity. This is not a model-level feature — it's a pattern you implement in your application layer using a vector store.

Semantic caching is complementary to prompt caching, not a replacement. It excels for high-repetition FAQ-style queries (a support chatbot where 40% of questions are "how do I reset my password"). It requires an embedding model, a vector store, and careful management of cache staleness. The threshold question — how similar is similar enough to return the cached response? — is typically set around 95% cosine similarity, and tuning it is a tradeoff between precision and hit rate.

### The Economics of Prefix Caching

The numbers that make prefix caching the dominant cost optimization:

**Anthropic (Claude):**
- Cache write: **1.25× base input rate** (5-minute TTL) or **2× base input rate** (1-hour TTL)
- Cache read: **0.10× base input rate** — a **90% discount**

On Claude Sonnet 4.6 at $3.00/M input tokens: you pay $3.75/M to write a cache entry for a 5-minute window, and $0.30/M every time you read from it. If a cached prefix is read 10 times before it expires, you've paid $3.75 once and $0.30 × 10 = $3.00 for reads — versus $3.00 × 11 = $33.00 without caching. That's an 80% cost reduction on that prefix for a modest hit count.

**OpenAI:** the cached-input discount is *not* a single number across the catalogue — it varies by model generation. Historically it sat at 50% off for the GPT-4o family; on OpenAI's newest models it has moved toward 90% off, the same 0.10× read rate Anthropic charges. Check the rate for the specific model you're calling rather than assuming a catalogue-wide discount.

The write cost is the key variable to understand. It means caching isn't free — you pay a premium on the first request that populates the cache. The math only works in your favor if subsequent requests hit the cache frequently enough. For a system prompt that's sent with every request, the payback is almost instantaneous. For a large document that's only referenced a few times, you need to calculate whether the read savings justify the write cost.

The crossover point has a closed form. With a write premium `w` and a read rate `r` (both as multiples of the base input rate), the number of hits needed to break even is:

```
h* = (w − 1) / (1 − r)
```

At Anthropic's 5-minute tier (`w = 1.25`, `r = 0.10`): `h* = 0.25 / 0.90 ≈ 0.28` — which rounds up to **just one cache hit**. Check it directly: at exactly 1 hit (2 total requests) caching costs $3.75 + $0.30 = **$4.05**, against $3.00 × 2 = **$6.00** without caching. Already cheaper. Every subsequent hit is pure savings.

**When prefix caching helps — and when it doesn't**

- **Helps:** a stable system prompt, tool definitions, or reference documents sent with most requests; bursty traffic where many requests share a prefix inside one TTL window; prefixes comfortably above your model's minimum cacheable length.
- **Doesn't:** low-reuse prefixes where the 1.25–2× write premium never amortizes; low-traffic endpoints whose request inter-arrival time exceeds the TTL; and prefixes below the minimum cacheable length — older Claude 3.x models cache from 1,024–2,048 tokens, but newer models like Claude Haiku 4.5 require 4,096, so a "short but stable" prefix may never cache at all.

### Why Most Prompt Cache Implementations Fail

This is the mistake made by the security team in the introduction, and by a large majority of teams implementing caching for the first time:

**The prefix cache requires bit-for-bit identical content from the beginning of the prompt.** The cache is keyed on the exact token sequence starting from the first token. Any change — any character change, any field that varies between requests — resets the cache boundary at that point.

Imagine a template where the first part is static (system instructions, tool definitions) and somewhere in the middle there's a `session_id` or a `timestamp` or a per-user configuration field that changes on every request. Even though 90% of the prompt content is identical, the cache only covers the tokens up to the first difference. Everything after that point is recomputed from scratch on every request.

![Stable versus broken prefix layout: with the dynamic field at the tail the whole prefix stays cached; with it in the middle the cache collapses at that point](https://doimages.nyc3.cdn.digitaloceanspaces.com/006Community/2026-Community-Tutorials-Anish/Solutions-Engineering/Prompt-Caching-Jeff/Screenshot%202026-07-24%20at%2011.52.52%E2%80%AFAM.png)

*Same content, one field moved. Stable layout: the dynamic field sits at the tail, so the entire prefix stays cacheable. Broken layout: the field sits mid-prefix, and everything after it is recomputed on every request.*

This is why the security team's hit rate was 7%: they had a dynamic field — a threat identifier — embedded in the middle of their otherwise stable prompt template. The system prompt, all the analysis instructions, all the tool definitions were being recomputed every time because that one identifier broke the prefix match.

Moving the identifier to the end of the prompt — after all the stable content — restored the full prefix for caching. Hit rate went from 7% to 74% in a single deployment.

### The Step-by-Step Optimization Path

**Step 1: Identify your stable prefix**

Map your prompt structure. Categorize every component:

| Component | Stable? | Examples |
|-----------|---------|---------|
| System prompt / persona | Yes | "You are a helpful assistant..." |
| Tool / function definitions | Yes | Full tool schemas |
| Few-shot examples | Yes | Static examples |
| RAG context template | Mostly yes | Document format, section headers |
| Retrieved documents | Depends | Same docs = cacheable; per-query docs = not |
| User query | No | Changes every request |
| Session variables | No | User ID, conversation ID, timestamps |
| Per-request metadata | No | Request-specific context |

Your cacheable prefix is the longest leading sequence that stays identical across the majority of your requests. In most deployments, this includes the system prompt, tool definitions, and any fixed few-shot examples — typically 1,000–8,000 tokens of stable content.

**Step 2: Move all dynamic content to the end**

Restructure your prompt so the stable prefix comes first, uninterrupted, and all dynamic content follows at the end. This sounds obvious, but production prompts often accumulate dynamic fields organically — a session ID added here, a user preference injected there — and these insertions silently kill caching.

The target structure:
```
[System instructions — fully static]
[Tool definitions — fully static]  
[Few-shot examples — fully static]
[Retrieved context — stable template, variable content]
[User query — dynamic]
[Session metadata — dynamic, at the very end]
```

Concretely, with an Anthropic-style `cache_control` breakpoint, this is the difference between a prompt that never caches and one that almost always does:

```json
// BROKEN — session id sits inside the cached system block.
// Every request writes a new cache entry. Measured: 0% hit.
{
  "system": [
    {
      "type": "text",
      "text": "You are a threat analyst...\nSession: 8f3c-2201-aa19",
      "cache_control": { "type": "ephemeral" }
    }
  ],
  "messages": [{ "role": "user", "content": "Analyze this indicator..." }]
}

// FIXED — the static prefix is cached; the session id moves to the user turn.
// Measured: ~99% hit.
{
  "system": [
    {
      "type": "text",
      "text": "You are a threat analyst...",
      "cache_control": { "type": "ephemeral" }
    }
  ],
  "messages": [
    {
      "role": "user",
      "content": "Analyze this indicator...\nSession: 8f3c-2201-aa19"
    }
  ]
}
```

See DigitalOcean's [prompt caching how-to](https://docs.digitalocean.com/products/inference/how-to/use-prompt-caching/) for the exact request format.

**Step 3: Monitor cache hit rate as a first-class metric**

Cache hit rate should appear on your LLM operations dashboard alongside latency and cost. It's a leading indicator: a drop in hit rate often precedes a cost spike, and it surfaces prompt structure regressions before they become billing surprises.

Most provider APIs return cache usage in response metadata. Log it. Alert on it.

**Step 4: Understand cache TTL and plan around it**

Anthropic's cache TTL options (5 minutes or 1 hour) are not just pricing tiers — they're operational constraints. A low-traffic deployment where requests come in every 10 minutes will never see cache hits on the 5-minute TTL tier. Choose your TTL based on your expected request interval at the p50, not the burst peak.

For workloads with bursty traffic patterns (a daily batch run that processes thousands of requests in an hour, then goes quiet), the math strongly favors the 1-hour TTL even at 2× write cost — the write cost is paid once per hour, and the read savings accumulate across the burst.

### Production Validation: What 70% Cache Hit Rates Do to Latency

The cost savings from prompt caching are well-documented. Less discussed is the latency impact, which can be equally significant.

[Google's Vertex AI team documented](https://cloud.google.com/blog/products/containers-kubernetes/how-gke-inference-gateway-improved-latency-for-vertex-ai) that intelligent routing — which ensures requests with shared prefixes land on the same inference server that already has the prefix cached — doubled their prefix cache hit rate from 35% to 70%. The result: **TTFT cut by 35%** on context-heavy coding-agent workloads (Qwen3-Coder), and **P95 tail latency improved by 52%** on bursty chat workloads (DeepSeek V3.1). Those are two distinct traffic profiles with different bottlenecks — context-heavy workloads are bound by re-computation overhead, bursty workloads by queue congestion — not the same workload measured two different ways.

The mechanism: cache hits eliminate the prefill computation cost for the stable portion of the prompt. For a prompt where 4,000 of 4,500 tokens are cached, the model only runs prefill on 500 new tokens — roughly an 89% reduction in prefill work. Prefill is compute-intensive; skipping it is a meaningful latency win, not just a cost saving.

### First-Hand Measurement: Prompt Caching on DigitalOcean Serverless

To put numbers to this rather than quote a vendor figure, we benchmarked [DigitalOcean's serverless inference endpoint](https://docs.digitalocean.com/products/inference/details/pricing/#serverless-inference) directly (Claude Haiku 4.5 at $1.00/M input, $5.00/M output, a ~6,000-token shared prefix, 1,500 requests per layout across 3 runs). Two findings worth internalizing:

**First, caching here is explicit, not automatic.** DigitalOcean serverless uses the Anthropic-style model: you mark the stable prefix with an ephemeral `cache_control` breakpoint. Without that marker, the cache hit rate is **0%** no matter how cleanly your prompt is structured — and there's a minimum cacheable length (a ~2,300-token prefix didn't cache; ~6,000 did, consistent with the 4,096-token minimum for this model noted above — prefixes under ~4,000 tokens didn't cache for us at all). This is the 5-minute / 1-hour TTL mechanism described earlier, not vLLM's automatic prefix caching.

**Second, with the prefix correctly marked, the layout effect is dramatic.** Holding the model and token count constant and only moving the per-request dynamic field — from inside the prefix to the tail — the measured cache hit rate went from **0% to 99.3%**, and estimated input cost dropped from **$6.72 to $0.57 per 1,000 requests — roughly a 90% reduction**. That's in the range the 90%-off cache-read economics would predict: when 99% of your input is served from cache at 0.1× the rate, your input bill falls by roughly an order of magnitude. (Our measured reduction runs a few points above the simplest back-of-envelope estimate from hit rate and discount alone; if you reproduce this benchmark, treat the exact percentage as directional rather than a number to plan a budget around, and measure your own traffic shape instead.)

*First-hand on DigitalOcean serverless (Claude Haiku 4.5, ~6,000-token prefix, 1,500 requests per layout): marking the prefix with `cache_control` and moving the dynamic field to the tail took the hit rate from 0% to 99.3% and cut input cost roughly 90% ($6.72 → $0.57 per 1,000 requests).*

One honest caveat from the data: on shared serverless, the *reproducible* win is **cost**, not throughput. Across runs, TTFT and throughput fluctuated with queue conditions while the cost reduction held steady. ### Semantic Caching: The Complement for High-Repetition Workloads

For workloads with high query repetition — customer support, FAQ bots, knowledge base search — semantic caching can complement prefix caching to eliminate full inference entirely for common queries.

The pattern:
1. On each request, compute an embedding of the incoming query
2. Check the vector store for semantically similar previous queries (typically ≥95% cosine similarity)
3. If a match is found, return the cached response immediately — no model call
4. If no match, run inference and store the result

The economics are compelling: a cache hit has near-zero marginal cost (one embedding call + one vector lookup). For a support bot where 40% of questions are variations of "how do I reset my password," semantic caching can eliminate nearly half of all inference calls.

The tradeoffs to manage:
- **Staleness:** Cached responses need a TTL or invalidation mechanism. A support response that was accurate last month may be wrong after a product update.
- **Threshold tuning:** Too high a similarity threshold → few hits. Too low → wrong responses returned for different queries. 95% cosine similarity is a reasonable starting point, but tune it against your specific query distribution.
- **Security:** Semantic caching can create information leakage risks in multi-tenant deployments — one user's query might return another user's cached response if queries are similar but contexts differ. Namespace your cache by tenant.

### The Common Pitfalls Checklist

Before declaring your caching implementation complete, verify:

- [ ] No dynamic fields (timestamps, session IDs, user IDs, per-request metadata) are embedded inside the stable prefix
- [ ] Retrieved documents follow the stable prompt template but appear after the fixed prefix
- [ ] Cache hit rate is logged per deployment and monitored via alerting
- [ ] Cache TTL is matched to your traffic interval — not set to 5 minutes for a workload with 10-minute inter-arrival times
- [ ] For multi-tenant deployments, semantic cache entries are namespaced by tenant
- [ ] Cache write costs are tracked separately — they're a real cost that partially offsets read savings
- [ ] Prompt structure is version-controlled — accidental prompt changes invalidate the cache silently
- [ ] Your prefix meets the minimum cacheable length for your specific model version, not a generic "1,024 tokens" assumption — newer models can require more

### Common Questions

**What is prompt caching, and how is it different from a KV cache?**
A KV cache is automatic and lives *within* a single request — it stops the model recomputing attention over tokens it has already processed while generating a response. Prompt (prefix) caching extends that reuse *across* independent requests, and unlike the KV cache it depends on how you structure your prompt.

**Why is my cache hit rate low even though I've enabled caching correctly?**
Almost always because a dynamic field — a session ID, a timestamp, per-user config — sits inside what you think is the static prefix. The cache is keyed on the exact token sequence from the first token, so the first difference truncates it. The other two causes are a prefix below the model's minimum cacheable length, and traffic too sparse for the TTL.

**Does prompt caching change the model's output?**
No. Cached prefixes reuse computed attention states for identical tokens; the model sees the same input either way. Caching is a cost and latency optimization, not a behavioural one.

**What's the minimum prompt length that can actually be cached?**
It depends on the model generation. Older Claude 3.x models cache prefixes as short as 1,024–2,048 tokens; Claude Haiku 4.5 requires 4,096. Don't assume a generic threshold — check the model you're actually calling.

**How many cache hits does it take before caching saves money?**
With a 1.25× write premium and a 0.10× read rate, `h* = (w − 1) / (1 − r) = 0.25 / 0.90 ≈ 0.28` — so a single hit already puts you ahead. At the 1-hour TTL tier (2× write) the break-even moves to about 1.2 hits.

**Is OpenAI's cached-input discount the same as Anthropic's?**
Not universally. Anthropic charges a consistent 0.10× read rate. OpenAI's discount varies by model generation — historically 50% off for the GPT-4o family, closer to 90% off on its newest models.

**Can prompt caching and semantic caching be used together?**
Yes, and they're complementary. Prefix caching cuts the cost of the prompt you still send; semantic caching avoids the inference call entirely for repeat queries. Prefix caching is model-level, semantic caching is something you build in your application layer.

**Does moving a dynamic field to the end always fix a low hit rate?**
No. It fixes the most common cause, but not a prefix below the minimum cacheable length, traffic sparser than the TTL, or "stable" content that isn't actually stable — a system prompt assembled with a timestamp or a randomly ordered tool list will still miss.

### Summary

Prompt caching is not a configuration checkbox — it's a structural property of your prompts that requires deliberate design.

The mechanics: prefix caching reuses computed attention states for identical leading tokens across multiple requests. A 90% discount on reads means the math is almost always favorable once a prefix is read even once more. The prerequisite is a prompt structure where all dynamic content follows the static prefix.

The single most common failure mode: a dynamic field embedded in the middle of an otherwise static prompt, reducing the effective cache prefix to the tokens before that field. Moving that field to the end of the prompt can take a deployment from 7% to 74% hit rate in a single change.

The three-layer caching stack:
1. **KV cache** — automatic, in-request, always on
2. **Prefix/prompt cache** — cross-request, controlled by prompt structure
3. **Semantic cache** — application layer, for high-repetition query patterns

With all three layers operating effectively, 60–80% of inference cost can be served from cache — reducing both cost and latency simultaneously.
