*為什麼認真的團隊預設就採用多供應商推論——以及 DigitalOcean 的第一方 Inference Router 落在哪裡，附上 `inference.do-ai.run` 上有紀錄的實測成本數字。路由模式與供應商無關；DO 專屬數字來自公開的 API 實測，而非行銷說法。*

### 前言

每一家推論供應商的銷售劇本裡，都有一個段落在說明你為什麼應該把業務整合到他們身上。常見的賣點包括：擔心被競爭對手綁定（lock-in）、管理多組 API 金鑰所帶來的營運複雜度，以及單一帳務關係的便利性。

劇本沒說的是：最成熟的買家——那些大規模運行 AI 的團隊，那些真正懂行的人——幾乎清一色都是「刻意」採用多供應商設計。他們把批次工作導向最便宜的端點、把即時查詢導向最快的端點、把小眾模型導向擁有它的供應商，並把對合規敏感的工作負載導向具備認證的供應商。他們是刻意這麼做的，不是偶然。

面對這個現實，正確的回應不是去抗拒它，而是要在其中成為有用的一環。

本文涵蓋多供應商路由在 2026 年如何運作、團隊用來實作它的工具，以及推論供應商的第一方路由（first-party routing）在什麼地方改變了整個盤算。

### 重點摘要

* 對認真的團隊來說，多供應商路由是*預設*的架構——是要去設計的對象，而不是要去對抗的問題。
* 驅動因素是結構性的：沒有任何供應商擁有所有模型；API 正常運作時間（uptime，約 99.1–99.8%）低於傳統基礎設施的水準，因此故障轉移（failover）是必備的；同一個模型在各家 serverless 供應商之間價格約相差 2×（而跨模型層級則高達 60× 以上）。
* 依約束條件路由：批次 → 最便宜、即時聊天 → 最低 TTFT、小眾 → 最廣的目錄、合規 → 具認證的地區，再加上一條後備路徑。
* 為 **goodput（有效吞吐，按 SLO 完成且正確的請求）** 進行最佳化——而不是為原始的 tokens/秒或最便宜的 token。
* 與 OpenAI 相容的 API 讓切換供應商只是改一個 base-URL，所以綁定效應很弱；第一方路由（DO Inference Router，「最高可達 67%」）的差異化在於營運層面，而不是把你困住。
* 對歐盟要誠實：今天所有供應商的無伺服器（serverless）推論都僅限美國，因此歐盟資料落地（data residency）目前意味著在歐盟 GPU 基礎設施上使用專用（dedicated）推論。

### 2026 年的現實：多供應商是預設值

在運行嚴肅生產環境工作負載的團隊之間，「全押在單一推論供應商上」愈來愈罕見。驅動因素是結構性的：

**1. 沒有單一供應商擁有完整目錄**

模型版圖已經碎片化。前沿封閉模型（Claude、GPT-5、Gemini）必須直接向各自的供應商取得。開放權重模型則跑在 Together、Fireworks、Groq、Replicate，或你自己的基礎設施上。特化模型——醫療編碼、法律推理、程式碼專用——往往落在精品型的供應商手上。沒有任何單一供應商能以最佳效能與價格同時提供以上全部。

**2. 可用性缺口讓故障轉移有其正當性**

傳統雲端基礎設施的 SLA 跑在 99.9% 以上。LLM API 的可用性達不到這個水準。某個第三方監測機構（[TokenMix 的 30 天滾動數據](https://tokenmix.ai/blog/best-llm-api-providers)）回報主要供應商落在約 99.1–99.8% 的區間，表現最差者約為 97.2%（大約每月 20 小時的停機時間）。請把任何單一這類數字當作方向性參考，而非權威結論——供應商會發佈自己的狀態頁，而你*實際量測到*的可用性取決於你的地區、模型與流量型態。但結構性的論點在每個來源都成立：生產環境的 LLM API 都低於你對成熟雲端基礎設施所期待的 99.9% 以上。對於 AI 層處於關鍵路徑上的應用而言，這就要求一套故障轉移策略——請對照每個候選供應商的狀態頁去驗證其真實數字，而不是依賴任何彙整平台的表格。

這不是針對任何特定供應商的批評——LLM 推論要做到可靠，本來就比一台靜態檔案伺服器難得多。這是這項技術在目前成熟度下的結構性特性。把這個區間換算成小時來看：在 30 天的月份裡，99.8% 大約是 1.5 小時的停機、99.1% 大約是 6.5 小時，而 97.2% 大約是 20 小時。如果你的應用無法在一個月內吸收單一供應商數小時的不可用，你就需要不止一家。

**3. 價差讓路由在經濟上合理**

同一個開源模型在各家 serverless 供應商之間，價格大約相差 2×。以 Llama 3.3 70B 為例（2026 年 6 月）：[Groq](https://groq.com/pricing) 每百萬 token $0.59、[DigitalOcean](https://docs.digitalocean.com/products/inference/details/pricing/) $0.65、[Fireworks](https://fireworks.ai/pricing) $0.90、[Together](https://www.together.ai/pricing) $1.04——而批次層級（通常約打 5 折）會把低端再往下拉。單一供應商來看差距不大，但在大量批次工作負載上，即使 2× 也是把真金白銀留在桌上。（更大的槓桿在跨模型*層級*——見下文。）

而那還只是*同一個*模型在各供應商之間的差距。跨模型*層級*的價差遠大得多——這正是路由經濟學的另一半。以下是單一供應商上的即時價格階梯（[DigitalOcean 無伺服器](https://docs.digitalocean.com/products/inference/details/pricing/)，每百萬 token，2026 年 6 月擷取）：

| 模型 | 輸入 | 輸出 |
|-------|------:|-------:|
| Qwen3-32B | $0.25 | $0.55 |
| DeepSeek V3.2 | $0.50 | $1.60 |
| Llama 3.3 70B | $0.65 | $0.65 |
| Claude Haiku 4.5 | $1.00 | $5.00 |
| Claude Sonnet 4.6 | $3.00 | $15.00 |
| Claude Opus 4.8 | $5.00 | $25.00 |
| o1 | $15.00 | $60.00 |

*以上價格為 2026 年 6 月的資料，而且變動很快——供應商會調價、新增層級、下架模型，通知期都很短。在用這些數字編預算之前，請把你路由表裡的每一個模型都對照官方定價頁重新確認一次。*

![Price ladder of DigitalOcean serverless model tiers from Qwen3-32B to o1, a 60× input spread](https://res.cloudinary.com/iambigmomma/image/upload/v1784186478/blog/multi-provider-routing/price_ladder.png)

*同一家供應商、七個層級：每百萬輸入 token 從 $0.25 到 $15.00。真正關鍵的路由決策，是一個請求落在這個階梯的哪一階——而不是帳單上印的是哪家廠商的商標。*

在最便宜與最昂貴的層級之間，這是**輸入 60× 的價差、輸出超過 100× 的價差**——還只是在一家供應商上，你甚至都還沒開始跨供應商比較。整個路由的理由就建立在這個落差上：一個 0.25 美元模型就能正確處理的任務，如果你反射性地把它送到最頂層，成本就會貴上 60×。路由不過就是「不去這麼做」的紀律。

### 依約束路由：批次給最便宜、聊天給最低 TTFT

並非所有推論流量都有相同的需求。一套理性的路由架構會依流量的實際約束條件加以分類，並據此進行路由：

| 工作負載類型 | 主要約束 | 路由到 |
|--------------|-------------------|----------|
| 批次／離線處理 | 成本 | 最便宜的供應商、批次折扣層級 |
| 即時使用者聊天 | 延遲（TTFT） | 該模型 TTFT 最低的供應商 |
| 小眾／特化模型 | 模型可用性 | 擁有該特定模型的供應商 |
| 對合規敏感（醫療、法律） | 認證 | 通過 SOC2／HIPAA 認證的供應商 |
| 大量穩態 | 吞吐量 | 該工作負載 tokens/秒最高的供應商 |
| 後備／溢位 | 可用性 | 主要供應商失效時的次要供應商 |

把這想成一個貨運物流作業。一個經驗老到的貨主不會所有東西都用同一家貨運業者——他們用隔夜空運處理急件包裹、用陸路貨運處理大宗貨物、用區域型貨運業者處理最後一哩配送，並讓跨境的國際選項待命以因應跨國需求。智慧之處在於把貨物的需求對應到貨運業者的強項，而不是因為「比較簡單」就只用一家貨運業者。

![Field-guide schematic of a routing dispatcher sending workloads along Batch, Real-time, Niche, and Compliance routes](https://res.cloudinary.com/iambigmomma/image/upload/v1784186478/blog/multi-provider-routing/logistics_dispatcher.png)

*路由器就是一個調度員：它讀取每個請求上的約束條件——成本、延遲、模型可用性、認證——然後挑一條能滿足它的路線。這些路線就是上面那張路由表。*

那些把所有推論流量一視同仁的團隊——把每件事都透過單一供應商、單一層級導送——就等於是替所有東西都付隔夜空運的費率，連那些根本不急的貨物也一樣。

### LiteLLM 與 OpenRouter 早就在做這件事——第一方路由多了什麼

在討論第一方路由之前，值得誠實面對生態系統已經提供了什麼。你大概早就知道這些工具，說不定手上已經有一個跑在生產環境裡。

**LiteLLM** 是一套開源的 Python 程式庫，也是可自行託管的代理伺服器（proxy），透過與 OpenAI 相容的介面對外提供 100 多家 LLM 供應商。它處理供應商抽象化、後備邏輯、成本追蹤與速率限制。取捨在於：它是自行託管（營運負擔），並會增加延遲開銷。自行託管也代表相依鏈由你自己負責——這種規模的代理伺服器會拉進一大串傳遞相依套件，所以請鎖定版本，並像對待關鍵路徑上其他服務一樣追蹤安全公告。但對於擁有 Python 基礎設施、又有能力自行託管的團隊來說，它是一個經過驗證、社群龐大的選項。

**OpenRouter** 是一項代管的路由服務，在單一 API 與統一帳務背後集合了來自數十家供應商的 300 多個模型。它接受一個依優先順序排列的模型陣列，並在主要模型失效、被速率限制或拒絕時自動嘗試下一個。它無法自行託管，但完全卸下了營運負擔。取捨在於：你在關鍵路徑上又多加了一個代管的相依套件，而且你對路由決策的可見度比自行託管的方案要低。

**Portkey、Bifrost 與其他工具**佔據著類似的位置——都是代管的閘道（gateway），在可觀測性、成本追蹤與企業功能上各有偏重。

重點在於：**這些工具確實存在、確實能用，而且只要你評估過路由，大概都已經看過它們。**如果 OpenRouter 已經接進你的技術堆疊，那麼「你不需要它，直接用單一供應商就好」不是論點——那是在要你把能跑的程式碼拆掉。更值得問的是一個更小的問題：第一方路由能給你什麼是第三方閘道給不了的？

### 第一方路由：DigitalOcean Inference Router

DigitalOcean 的 [Inference Router](https://docs.digitalocean.com/products/inference/how-to/use-inference-router/) 是一個內建於推論平台本身的第一方路由層——不是一個連接到多家供應商的第三方閘道，而是一項原生能力。在代管的推論平台之中，這種第一方路由仍不常見；如今大多數的多供應商路由都是透過疊加在上層的第三方閘道來完成。

這在實務上意味著：

- **沒有額外的延遲跳轉**——路由決策發生在平台內部，而不是透過一個會多增加一次網路往返的外部代理
- **整合帳務**——不需要與閘道供應商建立另一套帳務關係；路由是同一個帳戶的一部分
- **跨模型路由，不需自訂程式碼**——路由器會自動在模型層級之間移動請求，把簡單查詢送到較小的模型、把複雜的升級到較大的。它在真實工作負載上省下多少，下一節有實測；DigitalOcean 自己的行銷數字是「最高可達 67%」（[根據 DigitalOcean](https://www.digitalocean.com/blog/whats-new-on-gradient-ai-platform)，另有客戶案例回報相近幅度），但請把任何廠商公布的數字——包括這個——當作方向性參考，直到你用自己的流量跑過為止
- **不必重新部署就能重新設定**——路由策略存在平台裡，而不是你的應用程式裡，所以要換哪個模型服務你的流量，是一次 API 呼叫，而不是一次發版
- **可觀測性集中在一處**——路由決策、延遲、成本與快取命中率，都和你其餘的基礎設施顯示在同一個儀表板上

差異化並不在於 DO 路由比 LiteLLM 更會路由——兩者都會路由請求。差異化在於營運層面：第一方路由消除了一個相依套件、縮小了整合面，並讓路由邏輯保留在推論實際運行的平台之內。

### 路由到底省下多少，實測

路由的理由，建立在一個量測上：**模型選型稅**。在 `inference.do-ai.run` 上有紀錄的 2026 年 6 月實測——同一個分類提示、相同的 token 形狀（94 輸入 / 80 輸出），只換模型：

| 模型 | 每次成本 | 對比最便宜 |
|-------|---------------:|------------:|
| `openai-gpt-oss-20b` | $0.0000407 | 基準 |
| `openai-gpt-5` | $0.0009175 | 22.5× |
| `anthropic-claude-4.6-sonnet` | $0.0014820 | 36× |

這是**光在費率上就 36 倍的價差**。每月 70 萬次分類呼叫下，把每一次都送給 Sonnet（而其實小模型就能過關）要花 **$1,037.40，而不是 $28.49**。在一份有紀錄的[成本治理實測](https://www.digitalocean.com/community/tutorials/inference-router-multi-model-api-cost-governance)中（70 萬 / 25 萬 / 5 萬 的分類 / 問答 / 推論組合），router 分派把每月成本**相較 Sonnet-only 降低 39.6%、相較 Opus-only 降低 63.7%**。用你自己的金鑰重現每次請求的差距：

```bash
curl -s -X POST "https://inference.do-ai.run/v1/chat/completions" \
  -H "Authorization: Bearer $MODEL_ACCESS_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "openai-gpt-oss-20b",
    "temperature": 0,
    "messages": [
      {"role": "system", "content": "Classify the ticket. Reply with one word: billing, bug, how-to, or account."},
      {"role": "user", "content": "I was charged twice for my subscription last month."}
    ]
  }' | python3 -c "import sys,json; print(json.load(sys.stdin)['usage'])"
```

換成 `anthropic-claude-4.6-sonnet` 再比對 `usage` 區塊——那個差距就是你的帳單今天正在扛的路由稅。完整設定與 `x-model-router-selected-route` 回應標頭見 [Inference Router how-to](https://docs.digitalocean.com/products/inference/how-to/use-inference-router/)。

**什麼時候用哪一種路由層：**

- **第一方（DO Inference Router）**——你的主力工作負載跑在 DO 上，想要沒有額外延遲跳轉、沒有另一張帳單、只有一個儀表板的路由。DO 是你主要供應商時最合適。
- **第三方閘道（LiteLLM、OpenRouter）**——你橫跨 DO 沒託管的供應商，或需要一個能完全掌控路由邏輯的自管代理。接受多一個跳轉與相依。
- **單一供應商、不用路由器**——低流量、單一工作負載類別、單一模型層級。在流量真正混合簡單與複雜任務之前，路由的額外開銷不值得。

### 換掉流量所用的模型，不該需要重新部署

到目前為止，路由的論證都圍繞著成本。但還有另一個性質，隨著系統活得越久越重要：**模型這個決定被存放在哪裡。**

如果模型名稱是你應用程式裡的一個字串，那麼採用一個更新的模型就是一次程式碼修改、一次審查、一次發版，外加一套回滾計畫——而且每一個呼叫它的服務都要來一遍。如果模型決定存放在路由策略裡，那它就只是一次設定變更，應用程式甚至不會知道發生過這件事。

我做了一個 demo 來驗證這件事真的成立，而不是假設它成立。兩條 lane 服務同一串請求：一條把模型寫死，一條呼叫 router。在請求串進行到一半時，透過 API 重新排序 router 的模型排名：

```
PUT /v2/gen-ai/models/routers/{id}
```

在那之後的每一個回應，都由新排名的模型服務。觀察到的傳播時間大約兩秒。**零客戶端修改、零部署，而且切換過程中沒有任何失敗請求。**

真正讓這件事可查證、而不只是一個宣稱的關鍵是：回應中的 `model` 欄位是伺服器端寫入的，而且每個回應都帶有 `x-model-router-selected-route` 標頭，顯示平台選了哪一條路由。你不需要相信客戶端說是哪個模型回答的——你可以直接從回應讀出來，再跟你的品質指標對照。

這正是每次有新模型發表時都會冒出來的那個問題的實務答案：*我們要怎麼在不中斷線上流量的情況下採用它？* 如果模型是寫死的，答案會牽涉到一整列發版流程。如果它在 router 後面，答案就是改一次排名，加上一個事後可以驗證的回應標頭。

### 路由與提示快取，方向是相反的

有一個張力，在別人向你推銷路由時不會提到：**每一個被你路由走的請求，都是一個沒有打到熱快取的請求。**

[第 3 篇](/blog/zh-prompt-caching)從另一個方向量測過這件事。前綴快取讓輸入成本降低約 90%——但那是因為一個穩定的前綴反覆落在同一個端點上，而且落在快取 TTL 之內。路由同時攻擊了這兩個前提：

- **換了目的地，快取是冷的。** 每一家供應商、每一個模型都各自保有自己的前綴快取。把同一段系統提示送給三個模型，你就填充了三份獨立的快取，等於把 1.25–2× 的寫入溢價付了三次，而不是一次。
- **流量被拆散，間隔就變長。** 把一個工作負載拆成四路，每個目的地看到的請求速率只剩四分之一，於是請求之間的間隔變成四倍長。第 3 篇的實測對接下來會發生什麼講得很直白：請求間隔時間超過 TTL 的端點，根本累積不到任何命中。一個在滿載流量下運作順暢的 5 分鐘 TTL，在只剩四分之一流量時可能完全失效。

哪一邊會贏由算式決定，而把兩個價差並排來看，其實差距很明顯：

| 槓桿 | 數量級 | 來源 |
|-------|-------------------|------|
| 往下路由一個模型*層級* | 該請求最高 36× | 前述實測 |
| 輸入 token 的前綴快取 | 被快取部分約 10× | [第 3 篇](/blog/zh-prompt-caching) |
| 同一個模型、不同*供應商* | 費率約 2× | 前述價格表 |

**跨層級路由；但不要把同一個層級拆到不同供應商。** 把一個分類任務送到便宜 36 倍的模型，價值遠高於你因此放棄的任何快取——而且其實你什麼也沒放棄，因為不同的任務本來就有不同的前綴，本來就不會共用那筆快取項目。但是把*同一個*工作負載類別拆到不同供應商、去追那約 2× 的費率差距，卻可能在輸入側把約 10× 的快取效益還回去。這筆交易通常是虧的，而它正是團隊在「為了韌性」而在兩家供應商之間設定輪詢負載平衡時、不小心做下的那個決定——然後困惑於輸入帳單為什麼變高了。

兩個實務上的推論：讓每一條路由的流量密度足以撐過 TTL；並且把故障轉移路徑預設當成**冷的**——故障轉移後最初那批請求，會在一個還不存在的快取上付全額，這件事值得在你估算一次故障的成本之前先知道。

### 為 goodput 最佳化，而不是每秒 token 數

大多數團隊用每秒 token 數或每秒請求數來思考推論效能。這些指標很重要，但並不完整。

正確的指標是 **goodput**：在目標 SLO 內完成、且回傳正確、可用回應的請求。一個每秒處理 1,000 筆請求、卻有 15% 逾時、另有 10% 回傳幻覺的系統，其 goodput 是 750 筆「在 SLO 內且正確」的回應——而不是 1,000。

這個重新框定改變了你思考路由的方式：

- **原始吞吐量**（tokens/秒）是供應商指標，對容量規劃有用
- **TTFT** 是使用者體驗指標，對同步應用至關重要
- **在目標延遲下每筆正確回應的成本**才是商業指標

當你為 goodput 而路由時，決策矩陣看起來就不一樣了。Groq 的 LPU 在 Llama 3.3 70B 的輸出上提供市場上數一數二的吞吐量——數字很亮眼。但如果你的 SLO 是端到端 500ms 延遲，而 Groq 的佇列深度偶爾造成 800ms 的回應，那麼 Groq 的吞吐量數字幫不了你。為 goodput 而路由，不要為原始規格而路由。

### OpenAI 相容性因素：綁定效應比看起來更弱

多供應商路由在 2026 年之所以在結構上很容易，有一個原因：幾乎每一家推論供應商都對外提供與 OpenAI 相容的 API。在大多數情況下，切換供應商就是改一個 base URL 與一組 API 金鑰。就這樣。

這讓供應商綁定的論點比三年前弱了非常多。一個說「你加第二家供應商會有整合的痛苦」的供應商，描述的是一個自 2023 年以來就不再成立的現實。供應商之間的正面對決（bake-off）成本很低。遷移不是一個六個月的專案——而是一天的工作。

由此可得的推論是：唯一可持續的差異化形式，是在你「實際的」工作負載上可量測地更好的效能，而不是讓切換變痛苦的摩擦力。

### EMEA：無伺服器推論目前僅限美國

在主要的純推論（pure-play）供應商之中，存在一個有意義的地理缺口。**Together AI、Fireworks AI 與 Groq 都只從美國的資料中心運行無伺服器推論。**如果你有 GDPR 的要求，這不是偏好問題——而是合規的阻斷因素。在許多情境下，個人資料在法律上不得於歐盟／EEA 之外處理。

DigitalOcean 在[阿姆斯特丹（Amsterdam）營運歐盟 GPU 基礎設施](https://www.digitalocean.com/blog/digitalocean-bare-metal-gpus-eu-data-center)（NVIDIA 裸機 GPU），這讓「資料落地於歐盟」的推論今天就可透過在該基礎設施上進行**專用／自行管理**的部署來實現。

不過要對目前的狀態說清楚：**目前沒有任何供應商——包括 DigitalOcean——在歐盟地區提供*無伺服器*推論端點。**無伺服器推論目前全面都僅限美國。所以對於今天一個對 GDPR 敏感的歐洲工作負載而言，務實的路徑是在歐盟 GPU 基礎設施上做專用推論，而非無伺服器。「歐盟的無伺服器」這個缺口是真實存在、至今無人填補的——值得誠實地把它講清楚，而不是當成一項已交付的能力。

如果你要服務歐洲的使用者，請在挑架構之前就把這件事定案。問題不是「你偏好歐盟資料落地嗎？」——而是「你的法務團隊能核准在歐盟之外處理資料嗎？」對相當一類應用而言，答案是不能，而這個決定在任何跑分之前就先限縮了你的供應商清單。

### 為韌性而設計：如果你需要 99.9% 以上

如果你的可用性要求超過任何單一推論供應商所能交付的水準——而 99.9% 以上高於大多數供應商生產環境 API 的量測表現——那麼後備架構就不是選配項。

一個最小化的韌性架構：
1. **主要供應商**——你主力工作負載類別中表現最佳的選項
2. **次要供應商**——相同模型或同等品質、不同供應商
3. **故障轉移邏輯**——在主要供應商逾時、錯誤率達門檻或被速率限制時，自動路由到次要供應商
4. **斷路器（circuit breaker）**——防止重試風暴放大局部的中斷
5. **可觀測性**——觸發故障轉移時發出警報，並追蹤你已在次要供應商上運行多久

先前的路由分類法仍然適用：用主要供應商處理標準流量、用次要供應商作為故障轉移，並把不同類型的工作負載導向其適當的層級。架構不需要複雜——一個設定得當、含兩個供應商端點的 LiteLLM 或 Inference Router 配置，就能涵蓋大多數情況。

**這件事的程式碼其實少到什麼程度。** 在我做來觀察這個過程的 demo 裡，一個三步驟的 agent（retrieve → summarize → extract）在主要端點開始回傳 429 的情況下，用兩條 lane 服務同一個請求。兩條 lane 的 agent 程式碼一模一樣，唯一的差別是設定裡的一個 tuple：

```python
ENDPOINTS = (PRIMARY,)         # 單一端點 lane：把重試次數燒完，然後失敗
ENDPOINTS = (PRIMARY, ALT)     # 路由 lane：中途故障轉移，然後完成
```

單一端點那條 lane 耗盡重試後死掉。路由那條完成了任務，而且那條 lane 上的使用者完全不會知道發生過故障轉移——它只出現在決策日誌裡。（故障是由一個本地 proxy 注入的，所以每次執行結果都相同；這個練習展示的是故障轉移的行為，完全不能用來說明任何供應商真實的錯誤率。它也不是延遲基準測試——路由那條 lane 通常會在切換前多付一個失敗請求的錢。）

上面那份清單沒有涵蓋、但在生產環境會咬人的兩個失效模式：

**你的次要供應商是不同的模型，所以你的 eval 必須在兩邊都過。**「相同模型或同等品質」這句話承載了太多東西。如果次要端點是另一個模型——而跨供應商時通常就是——那麼故障轉移就是一次無聲的品質變動。請拿你的評測集去跑後備路徑，而不只是主要路徑，否則一次供應商事故就會變成一次沒人察覺的降級，最後只會從使用者抱怨裡浮現。

**故障轉移有帳單，不只有時長。** 如果次要端點在更高一個層級，一次六小時的事故就同時是成本事件與可用性事件。而且承接前一節：後備路徑在定義上就是冷的——切換後最初那些請求，會在一個還沒被填充的前綴快取上付全額。在你真的需要它之前先把這筆算出來，別讓事故檢討會是第一次有人做這個算術。

關鍵原則是：**刻意把後備路徑設計出來，而不是假設你的主要供應商永遠不會出狀況。**一個建立了韌性多供應商架構、並把其中一家當作主力工作負載類別主要端點的團隊，處境會比一個出於原則堅持單一供應商、第一次事故就手忙腳亂的團隊好得多。

### DigitalOcean 什麼時候該當你的主要供應商——什麼時候不該

要在多供應商架構裡替任何一家供應商定位，有用的問法是「它該當什麼的*主要*供應商」，而不是「它該不該是你唯一的供應商」。對 DigitalOcean，誠實的答案是：主力工作負載與路由控制平面的合理預設值，而在幾件特定的事情上則是錯的選擇。

它能勝任主要供應商的地方：
- 全端整合（推論 + 運算 + 向量資料庫 + 儲存），TCO 比多雲方案低 20–40%，根據 DigitalOcean 自己發表的 [Deploy 2026 分析](https://www.nasdaq.com/press-release/digitalocean-unveils-ai-native-cloud-built-inference-era-2026-04-28)——這是廠商自行發布的數字，請當作方向性參考，實際採信前先用你自己的技術堆疊算一遍
- 第一方路由層，無須第三方相依即可讓每個請求選到剛好夠用的模型
- 透過在阿姆斯特丹 GPU 基礎設施上的專用推論，達成歐盟資料落地（包含 DO 在內，目前尚無任何供應商提供「歐盟的無伺服器」）
- 單一 VPC、單一帳務關係、整合的可觀測性

它不該當主要供應商的地方：
- 如果你需要在模型發表當天就用上絕對最新的前沿模型，你會直接向 Anthropic／OpenAI／Google 取得
- 如果你需要 Together AI 那種開源模型目錄的深度，在 DO 上找不到同樣的廣度
- 微調（fine-tuning）與 LoRA 工作流需要不同的供應商（Together、Fireworks、Replicate）

由此推出的路由架構是：DO 處理主力工作負載、批次處理與 EMEA 合規需求；專家型供應商則透過路由層處理它們各自的利基。這不是讓步——而是一套誠實的架構，而且它比一個不符合你實際在建構什麼的單一供應商強制令要好。

### 常見問題

**跨多家供應商做路由會不會增加延遲？**
要看路由發生在哪裡。第三方閘道坐在你的應用與模型之間，所以你會多付一次網路往返——通常是幾十毫秒，這對 500ms 的 TTFT 預算有影響，對批次工作則沒有。內建在推論平台裡的第一方路由則完全省掉這一跳。在下結論之前先用你自己的流量量一次；路由器內部的決策時間，通常相對於網路路徑可以忽略不計。

**我的流量很小，還需要路由器嗎？**
大概不需要。路由要划算，前提是你的流量真的混合了不同的任務複雜度——便宜的分類和昂貴的推理並存——因為省下來的錢來自「不把簡單工作送到最高層級」。如果你只有一個工作負載類別、跑在一個模型層級上、量也不大，那麼路由器帶來的營運面增加，換到的只是幾塊美元。等流量開始多樣化、或每月帳單開始讓你有感時再回頭看。

**換供應商實際上要多久？**
只要供應商提供與 OpenAI 相容的 API——現在幾乎都有——那就是改一個 base URL 和一組 API 金鑰。真正慢的部分不是程式碼：在你的評測集上重新驗證輸出品質、從你的地區重測延遲、再跑一次你們公司要求的資安審查。請用「天」來估評測時間，而不是用「月」來估整合時間。

**路由器會不會把該用大模型的請求送去小模型？**
這正是真正的失效模式，也是為什麼可觀測性比省下的錢更重要。DigitalOcean 的 Inference Router 會在每個回應上帶回 `x-model-router-selected-route` 標頭，所以你可以記錄每個請求實際上是由哪個模型服務的，再和你的品質指標對接。如果某條路線分類錯誤，你會在這份資料裡先看到，而不是在使用者的抱怨裡。對於「降級絕對不可接受」的請求，就明確指定模型名稱來路由；其餘的再交給路由器。

**歐盟可以用無伺服器推論嗎？**
今天不行，而且任何供應商都不行。Together AI、Fireworks AI、Groq 與 DigitalOcean 的無伺服器推論全都由美國資料中心提供。如果你的資料不能離開歐盟／EEA，你的選項是在歐盟 GPU 基礎設施上做專用推論——DigitalOcean 在阿姆斯特丹有，其他幾家也有——而不是無伺服器端點。任何跟你說得不一樣的，講的是藍圖而不是現況。

**剛有更好的模型發表。我可以在不重新部署的情況下採用它嗎？**
如果模型名稱是你應用程式裡的字串，不行——那是一次程式碼修改，而且每個出現這個字串的地方都要改。如果你的流量走 router，可以：你透過 API 重新排序路由策略，之後的請求就由新模型服務，不需要客戶端修改、也不需要發版。在前述的 demo 裡，傳播時間大約兩秒，切換過程中沒有失敗請求。事後請用 `x-model-router-selected-route` 標頭去驗證，而不是假設；另外也請先拿你的評測集跑過新模型——一次毫無摩擦的切換，只有在你切過去的那個東西真的在你的工作負載上更好時，才算是優勢。

**那個 99.1–99.8% 可以直接寫進我自己的 SLA 嗎？**
不行。那是單一第三方監測機構 30 天視窗的數字，最多只能當方向性參考——你實際量到的可用性取決於地區、模型與流量型態。如果你要對自己的客戶承諾可用性，請從每家供應商公開的狀態頁與合約 SLA、加上你自己的量測來推導，並且把故障轉移路徑做到足以補上「你承諾的水準」與「任何單一供應商保證的水準」之間的落差。

**第一方路由是不是換了一種形式的 lock-in？**
它比看起來弱，理由和供應商綁定普遍偏弱是同一個：路由器講的是與 OpenAI 相容的 API，所以要拿掉它，等於把 base URL 指到別的地方。你會失去的是路由策略與單一儀表板的可觀測性，而不是你的應用程式碼。真正會把你鎖住的，是把路由邏輯寫在一套專有、不可移植的介面上——這一點在你採用任何閘道時都值得先確認，不管它是不是第一方的。

### 總結

多供應商路由不是對推論供應商的威脅——它是認真的團隊所建立的架構。原因是結構性的：沒有單一供應商擁有所有模型、可用性缺口要求故障轉移，而價差——同一個模型跨供應商雖然不大，但跨模型層級極為懸殊——讓路由在經濟上合理。

在實務上有效的路由分類法：
- 批次／離線 → 最便宜的供應商
- 即時聊天 → 最低 TTFT 的供應商
- 小眾模型 → 目錄最廣的供應商
- 對合規敏感 → 在正確地區具認證的供應商
- 後備 → 主要供應商失效時的次要供應商

工具早已存在（LiteLLM、OpenRouter、Portkey），而且你大概也已經評估過它們。第一方路由的差異化在於營運層面：沒有延遲跳轉、整合的帳務與可觀測性、路由邏輯就活在平台之內。

正確的框架是 goodput——在 SLO 內完成且輸出正確的請求——而不是原始的每秒 token 數。為「在目標延遲下每筆正確答案的成本」而路由，而不是為最便宜的 token。

EMEA 的定位是真實的：所有供應商的無伺服器推論都僅限美國，因此對 GDPR 敏感的歐洲工作負載來說，今天的歐盟落地意味著在歐盟 GPU 基礎設施上的專用推論（DO 在阿姆斯特丹就有），而非無伺服器。「歐盟的無伺服器」這個缺口至今無人填補——值得誠實地講清楚，而不是任何人可以宣稱的能力。

務實的目標是：為主力工作負載類別選定一家供應商、把它的路由層當作你的控制平面，並對哪些工作負載該放在別處保持誠實。那是一套能撐過生產環境考驗的架構。
